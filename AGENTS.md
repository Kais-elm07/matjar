## Design

Before any work on the interface, read `DESIGN.md` at the project root and follow it; it is the single reference for the store's colors, fonts, spacing and components. The mapping of its values to Tailwind classes is in the project skill `.claude/skills/design-system/SKILL.md`. After any change to `DESIGN.md`, run `pnpm design:lint`.

The skill `design-taste-frontend` (Taste Skill, from github.com/Leonxlnx/taste-skill) is installed for the user in `~/.claude/skills`, not in this repository. In this project it is used only to review the interface: it points out problems and suggests improvements. Suggestions are carried out only where they agree with `DESIGN.md`, following the `design-system` skill. Don't deal a palette or font pairing with its `start.mjs`, don't copy its `assets/` or `starter.html` into the store, which is a Next.js app, and don't add the skill's files to this repository.

## Code rules

- No `any`, no type assertions (`as`, including `as const`) and no non-null assertions (`!`). Use a type annotation, `satisfies`, or a type guard from `src/lib/guards.ts` (general checks) or `src/modules/catalog/guards.ts` (the catalog's shapes). Data read at runtime (what the browser downloads, browser storage, JSON columns in the database) is checked with a guard before it is used. ESLint enforces these rules.
- List keys come from the data (a slug, SKU or id), never from the position in the array. Loading placeholders take their keys from `placeholderIds()` in `src/lib/placeholders.ts`.
- One component per file, named after it in kebab-case (`PromoTile` in `promo-tile.tsx`). The exception is the compound components in `src/components/ui` (Dialog, Sheet, Tabs, Breadcrumb, NativeSelect), whose parts only work together. Shared class strings go in a styles file such as `product-styles.ts`.
- Every component that takes props has a `<Component>Props` interface right above it. When the props are a union, which an interface can't express, it is a type alias with the same name (`ListingViewProps`). Route files use Next.js's generated `PageProps<"/route">` and `LayoutProps<"/route">` types, and `ErrorInfo` from `next/error` for `error.tsx`.
- A component loaded with `next/dynamic` is rendered inside `Optional` (`src/components/shared/optional.tsx`), so a download that fails leaves that part out instead of replacing the page with an error page. A page's own errors go to `src/app/(store)/error.tsx`, and the store shell's to `src/app/global-error.tsx`.
- For React performance and component structure, follow the project skills `vercel-react-best-practices` and `vercel-composition-patterns` in `.claude/skills`, copied from github.com/vercel-labs/agent-skills.

## Server and data

- The store runs on a Next.js server with the classic rendering model (Cache Components is off). The catalog and help pages keep `generateStaticParams` (the product and category pages with `dynamicParams = true`, the help pages with `false`). The share images and robots keep `export const dynamic = "force-static"`; the data JSON files and the sitemap are `force-dynamic`, computed from the cached catalog, because on Netlify the catalog's tag does not refresh a route handler prepared at build time. A page that reads the database says so with `export const dynamic = "force-dynamic"`.
- Code that runs only on the server imports `server-only`. The database is reached only through `getDb()` in `src/lib/db.ts`, and the orders through `src/lib/checkout/orders.ts`.
- Server Actions (`"use server"`, such as `src/lib/checkout/actions.ts`) can be called by anyone with a POST request: check every argument with Zod, and take prices, stock and coupons from the server's own data, never from the browser.
- `placeOrder` may be sent twice for one order (the answer was lost and the visitor confirmed again), so it starts by looking for the order saved under the request's id, and `saveOrder` writes the order's row, with that id, before it lowers the stock. When it refuses because the cart is behind the store, it answers with the cart's current prices and stock (`cartIsBehind`), which the checkout applies without a reload.
- A `"use client"` module can't hand functions or constants to server code, so logic both sides need lives in a plain module (`src/lib/checkout/totals.ts`, `quantity.ts`).
- Server code reads files only by a literal path. A computed path makes Turbopack copy the whole project into the server's files; a check that runs only during `next build` is guarded by `NEXT_PHASE` and marked `turbopackIgnore` (`src/modules/catalog/build.ts`).
- Addresses end with `/` (`trailingSlash`), API routes included, and are built in `src/lib/routes.ts`.
- The root layout writes nothing into `<head>` by hand; Next fills it from `metadata` and `viewport`. Hosts add text there (Netlify puts a line break and a comment after `<meta charSet>`), and React then throws away the server's HTML and renders the whole page again in the browser. An inline script that must run before the page is drawn goes at the start of `<body>` (`RENDER_ALL_SCRIPT` in `src/lib/render-later.ts`).
- After changing `prisma/schema.prisma`, run `pnpm db:migrate` and then `pnpm db:generate`, and commit the migration. Migrations only add (new tables, optional columns), because a rollback on the host restores the code but not the tables. The browser tests run against `next start`: they need `pnpm build` and the local database (`pnpm db:start`, `pnpm db:deploy`, `pnpm db:seed`), and they reseed it before they run. `pnpm test:db` tests what needs the database itself (saving orders, the stock, the look of an uploaded photo); `pnpm test` stays without one. `revalidateTag` works only inside Next (a Server Action or a route), so code the database tests call doesn't call it.
- The catalog (categories and products) is in the database and is read only through `getCatalog()` in `src/modules/catalog/load.ts`, which caches the plain rows under the tag `catalog` (`unstable_cache` keeps JSON, so never cache the built catalog, which holds `Map`s). The catalog functions are async. A change to products or stock ends with `revalidateTag("catalog", "max")`. The share images (`src/app/og`) read `getBuildCatalog()` instead, outside the cache, because they need the photos in `public/images`, which the server's functions don't carry: they must never be drawn again at runtime. Their routes take `dynamicParams = true` and start with `shareImageOutsideBuild()` (`src/lib/og/render.ts`), which answers a request outside `next build` (a product or category added after the deploy) with a redirect to the site's image. The unit tests build the catalog from `src/data` instead (`tests/unit/support/catalog-load.ts`, swapped in by `vitest.config.mts`).
- The admin panel (`src/app/admin`, `src/lib/admin`): every admin page calls `verifyAdmin()` and every admin Server Action starts with `isAdmin()`, next to the data; there is no `proxy.ts`. Admin reads and writes go to the database directly (`src/lib/admin/catalog.ts`), and every write ends with `revalidateTag("catalog", "max")`. Products are hidden, never deleted, because orders name their SKUs. The browser tests sign in with the password in `tests/e2e/admin-password.ts`, whose hash `playwright.config.ts` gives the test server; no real password or hash is written in the project.
- Photos uploaded in the admin panel go to Supabase Storage only through `src/lib/admin/uploads.ts`, which prepares them with `src/lib/images/prepare.ts`, the same module `pnpm images` (`scripts/images.ts`) uses. The secret key stays on the server; `SUPABASE_URL` is public and joins the CSP's `img-src` at build time. A photo's address, local or uploaded, is written without its size and extension, and `src/lib/image-loader.ts` adds them. The browser tests upload to a fake storage (`tests/e2e/fake-storage.ts`), never to Supabase.
- The catalog tables are filled from `src/data` by `prisma/seed.ts`, which converts the files with the pure functions in `src/modules/catalog/rows.ts`. The seed runs outside Next (through `tsx`), so nothing it imports may import `server-only`.

## Language

The project documentation (`README.md`, `PLAN.md`, `DESIGN.md`, `DEPLOYMENT.md`, `USER-TESTING.md` and the design skill), code comments, test names, CI step names and commit messages are written in English. A comment that refers to interface text quotes it in Arabic with its English meaning, such as "تصفية" (Filter). The storefront stays in Arabic: interface text, product and category data, the static pages in `src/content/pages`, and the validation and error messages the store owner and the visitors read, including the output of the scripts in `scripts/`.
